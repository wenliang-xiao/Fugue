## 1. 背景与问题

Agent harness 已经百花齐放（OpenCode、Pi、Claude Code、Codex、DeepSeek Harness、Hermes……），一个开发者手上往往同时有多个。但它们各自是"一个终端 / 一个桌面窗口"，带来四个痛点：

| 痛点 | 现状 | 后果 |
|------|------|------|
| **入口割裂** | 每个 harness 一个入口 | 想用几个就得开几个窗口，来回切 |
| **绑在本地** | 入口是本地终端/桌面 | 离开电脑就断了；云端 harness（如 Hermes）没有统一入口 |
| **对话阻塞** | 一问一答 | 复杂任务只能干等，无法边聊边干 |
| **没有语音** | 几乎都是文本 | 边走边说 / 开车等场景基本无解 |

**核心洞察**：缺的不是"第 N 个 agent harness"，而是一个**编排层**——把"前台对话"和"后台干活"拆开：前台永远在线陪你聊，后台把任务委派给你已有的多个 harness 并行执行，干完主动插话汇报。

---

## 2. 目标用户

| 画像 | 特征 | 典型场景 |
|------|------|---------|
| **个人重度用户（首要）** | 手上已有 ≥2 个 harness（本地 + 云端），飞书重度使用，想要语音 | 本地 OpenCode/Pi 写代码，云端 Hermes 跑长任务，飞书 + 语音统一入口 |
| 小团队 | 多人共用云端 harness，需要统一入口与状态同步 | 团队共享 Hermes 实例，各自从飞书/语音接入 |
| 早期采用者 | 关注 agent 编排、愿意折腾开源工具 | 基于本项目二次开发 |

> 首版聚焦**个人重度用户**，小团队作为第二阶段的自然延伸。

## 3. 竞品与差异化

| 竞品 | 定位 | 与我们差异 |
|------|------|-----------|
| Hermes Agent（252k★） | 云端自进化 agent，自带 Telegram/Discord/Slack（**无飞书**） | 它是"一个 agent"，不是"编排多个 harness"；无飞书 |
| cc-connect（15.8k★） | 本地 agent → 20+ IM 桥接 | **同步 console 转发**，非异步编排；无 Hermes |
| ccteam（648★） | 多 vendor agent 组队编排 | 最接近，但无 Hermes、无全双工语音、飞书二等 |
| dsh-lark-*（多个，2~40★） | dsh → 飞书桥接 | 单 harness 浅桥接，重复造轮子 |

**我们的定位**：**异步对话编排，而非同步桥接**。

| | 桥接（cc-connect/botmux） | 编排（本项目） |
|---|---|---|
| 交互模式 | 发指令 → 执行 → 回结果（同步 console） | 派活 → 继续聊 → 后台并行 → 主动播报 |
| 体验 | 远程操控一个终端 | 跟一个助手打电话 |
| 多任务 | 基本串行 | 多后台并行，随时问进度/取消/补信息 |
| 全双工语音 | ❌ | ✅ 核心卖点 |
| 多 harness | 弱（单/多 CLI 转发） | ✅ 可插拔，路由/手动指定 |

**差异化结论**：唯一同时具备「全双工语音 + 多端共享 + 多 harness 编排 + 支持云端 Hermes」的开源编排层。

## 5. MVP 边界

**MVP（P0）只做一件事，验证核心假设**：*"全双工语音 + 飞书文本，共享同一个 agent 编排层，能把任务委派给一个 harness 并主动播报"*。

明确包含：
- 语音入口用 qwen-audio-agent 现成的 WebUI / 桌面 orb（不新写语音 client）
- 飞书入口自写 `text_only` client
- 单 harness（默认 OpenCode），多 harness 走 P1
- 任务生命周期完整（REQ-006）

明确不包含（MVP 不做）：
- 多 harness 路由（REQ-005，P1）
- 远端 Hermes（REQ-007，P1）
- 飞书语音消息（REQ-008，P1）
- 智能路由 / 成本账本 / 多用户（P2）

**MVP 验收**：能对着语音 App 全双工聊、插话打断；能在飞书里文字派活；两个入口看到同一个任务的进度与结果；任务完成时主动播报。

---

## 6. 非目标（Non-goals）

- 不再造一个 agent harness（复用用户已有的）。
- 不做飞书内的实时音视频通话（平台不开放第三方 RTC 接入，见 REQ-002 设计说明）。
- 不做通用 IM 矩阵（先只做飞书 + 语音 App；Telegram/Slack 等不在首版）。
- 不做多租户 SaaS（个人部署优先，多用户是 P2）。

## 7. 关键产品决策

### 决策 1：多端是"分时互补"，不是"同时并发"

用户不会一边打电话一边刷飞书。两个入口是**分时互补**关系：语音 App 用于"打电话式"深度交互，飞书用于"不方便出声"时的文字派活与异步通知。

- **实现含义**：两个 client **轮流连接同一个 Gateway**（利用 qwen-audio-agent 的 `session.takeover` + `session.replay` 机制），任务/记忆在 Gateway 层持久化共享。**无需改动 qwen-audio-agent core**。
- **代价**：不支持"语音通话中飞书实时同步推送"（语音期间，任务完成由语音通道直接播报，天然不冲突）。
- **若未来要"同时在线"**：需改 Gateway 的"单 client 约束"（架构级改动），作为 P2 评估项，非首版目标。

### 决策 2：语音全双工走"双通道"，不硬塞进飞书

飞书开放平台不开放第三方 RTC 接入（实时全双工语音流无通道），但开放语音消息（异步半双工）。因此：
- 真全双工语音 = 独立的语音 App（qwen-audio-agent 现成客户端）。
- 飞书语音消息（REQ-008，半双工）= P1 补充，非替代。

### 决策 3：不 fork qwen-audio-agent core，只用其标准扩展点

多 harness 走 `BackendPort` 适配器聚合，飞书入口走 Gateway Client Protocol。好处：跟随上游更新、可独立开源、改动面收敛。

## 8. 成功指标

| 指标 | 目标 | 度量方式 |
|------|------|---------|
| 双端无缝切换 | 飞书 ↔ 语音切换后，任务/会话状态 100% 一致 | 手工验收 + 自动化用例 |
| 对话不阻塞 | 派活后 2s 内前台可继续对话 | 自动化用例 |
| 全双工打断 | 语音打断延迟 < 300ms（体感无感） | 复用上游指标 |
| harness 可插拔 | 接入一个新 ACP harness ≤ 配置即可（零代码） | 文档 + 用例 |
| 主动播报 | 任务完成 → 播报延迟 < 1s | 自动化用例 |
