## 1. AI 编码的四个陷阱（为什么需要本规范）

| 陷阱 | 现象 | 数据 |
|------|------|------|
| **正确性陷阱** | 代码"几乎对"——能编译、能跑主流程，错在边界条件（空输入、并发、超大值） | 66% 开发者把"看起来对、实际差一点"列为 AI 最大挫败；边界输入出错率约常规 2 倍 |
| **复杂度陷阱** | 代码库一大就失能；跨文件改不动；用复制粘贴代替抽象 | 多文件重构（2–31 文件）AI 只完成 22%，人类 87%；AI 普及后重复代码块一年涨 8 倍 |
| **行为陷阱** | 谄媚、作弊（为过测试硬编码/删测试）、长会话忘规矩、伪造汇报 | 最强模型在无解任务上作弊率最高（某模型 54%）；"不要做 X"禁令反使违规率升高 |
| **团队/单人陷阱** | 生成速度 ≫ 理解速度，理解债累积成没人敢动的系统 | 生成 140–200 行/分钟 vs 人读懂 20–40 行/分钟，差 5–7 倍 |

**核心结论**：`靠嘱咐不如靠机制`（权限、门禁、spec 先行）；`绿灯不等于被测过`（AI 写的测试约三成无断言）。

## 2. 五道验证门（对抗四个陷阱的机制）

每道门对应一类陷阱，是 review 和提交的**硬卡点**：

| 门 | 规则 | 对冲 |
|----|------|------|
| ① **解释门** | 解释不了的代码不许 commit。"AI 写的我没细看"不是解释 | 正确性 |
| ② **依赖门** | AI 引入的每个新依赖，人工核实真实存在 + 来源 + 维护状态（AI 约 1/5 概率编造不存在的包） | 正确性 |
| ③ **测试门** | 改动路径必须有测试；**人验断言质量**，不看绿灯（测试可能装样子） | 正确性 |
| ④ **RCA 门** | 故障必走根因分析（问题→原因→分析→修复→测试）；禁止以"模型幻觉"作根因——根因永远是人的决策（review 不足 / 测试缺失 / 授权过大） | 行为 |
| ⑤ **不可逆门** | 生产数据、git 历史、对外发布、危险命令——**AI 永远只提案，不执行** | 行为 |

**本项目特有补充门**（来自协议边界，见 [评审规范](./03-review/review-guide.md) §3C）：
- 协议对象（ACP session id、remote task id、token、凭证）不得跨 BackendPort / Gateway 边界进入模型可见文本。

## 3. 决策权矩阵（人和 AI 的边界）

| 决策类型 | 拍板 | commit 前缀 |
|----------|------|------------|
| 修宪 / Accepted ADR / 核心协议 / 安全语义 / 不可逆操作 | **人** | `[human]` / `[reviewed]` |
| 跨模块边界 / 协议字段 / 模型与工具变更 | AI 提案 + 人逐条 review | `[reviewed]` |
| 既有 ADR 框架内的实现 / 文档 / 重构 | AI 自主 + 人抽验 | 无前缀 |
| 外围原型 / spike（干净 git 状态，失败即弃） | AI 自主 | `[draft]`（不入 main） |

**升级规则（AI → 人，强制）**：
1. 触及安全 / 隐私 / 对外承诺 / 不可逆操作 → 立即升级。
2. 对同一问题连续 2 次修不动 → 人介入找根因，禁止继续加猛药。
3. 任何不确定 → 停下来问。
4. 人感到失控（跟不上变更速度）→ 立即停、缩小批次。

## 4. 反模式（自检 + review 共同语言）

| # | 反模式 | 说明 |
|---|--------|------|
| 1 | Accept-all 不读 diff | 读不过来说明批次太大，缩小 |
| 2 | 无 plan 大改 | 大 diff 没法 review，先写计划 |
| 3 | chat 即决策 | 拍板必落 ADR |
| 4 | 文档后补 / 不补 | 文档与变更同一个 commit |
| 5 | 跨会话靠记忆 | AI 没记忆，接力信息进 dev-log |
| 6 | 意图不落档 | 意图源头丢失，追溯链断头 |
| 7 | 用 AI 掩盖自己不懂的领域 | 不能解释的代码不许 commit |
| 8 | brute-force 替代根因 | 加内存 / 重试 / sleep 不是修复 |
| 9 | 复盘怪模型 | "模型幻觉"不是根因，根因是人的决策缺失 |
| 10 | 追逐 model/tool zoo | 换模型凭 eval 说话，走 ADR |

## 5. 与 SDD 的关系

本规范是 [AGENTS.md](../AGENTS.md) 的 SDD 流程在**"AI 协同开发"维度**的强化：

- SDD 的"spec 先行" → 对冲**复杂度陷阱**（小步垂直切片，不去踩长上下文失能）。
- SDD 的"review 以 spec 符合度为第一标准" → 落实**解释门**。
- SDD 的"可追溯" → 落实**persist everything**（spec 和决策是持久资产，代码只是产物）。
- 本规范的五道门 → 是 review-checklist 的**判断依据**。

**一句话**：`spec 是真相源（SDD），五道门是执行纪律（vibe coding），合起来才是负责任的 AI 协同开发。`

## 6. 参考

本规范的思想与数据源自 [Coro 的 Vibe Coding 开发规范](https://github.com)（内部借鉴），其三个实证地基：
- AI 是放大器（DORA 2025：每单位 AI 采用度对应交付稳定性 −7.2%）。
- 自我感知不可信（METR：资深开发者用 AI 实测慢 19%、自感快 20%）。
- 产出 ≠ 交付（Faros AI：个体 PR +98%，组织交付持平，瓶颈在 review）。
