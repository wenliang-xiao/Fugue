# ADR-0011 双产品形态：本地助手（A）+ 云端常驻（C），共享编排核心

- 状态：已采纳（用户拍板 2026-10-22）
- 日期：2026-10-22

## 背景

Fugue 当前是「本地跑」的形态（`npm start` 前台进程）。用户指出两个问题：① 进程需要手动启动、崩溃即挂（缺进程守护）；② 电脑合盖/休眠时助手不可用（本地跑的物理天花板）。

durable 只解决「崩溃恢复」，不解决「睡眠暂停」——睡眠时进程是暂停不是崩溃，launchd/durable 都救不了。因此「随时随地可用」与「纯本地」存在不可调和的矛盾。

## 决策

**拆成两个产品形态，共享同一套编排核心，只在「部署形态」上分化：**

| 维度 | A · 本地个人助手 | C · 云端常驻 |
|------|----------------|-------------|
| 核心价值 | 全双工调用多 agent + 整体会话管理/记忆 + 多 harness 分工 | 7×24 常驻，随时响应 |
| 可用边界 | 电脑醒着可用；合盖休眠即睡，唤醒后自动恢复 | 不受本地物理状态影响 |
| 进程生命周期 | launchd 守护（常驻 + 自启 + 崩溃自愈） | 云平台管理（容器/进程监督） |
| TaskWorld 实现 | world-file（本地 JSONL） | world-postgres / Redis |
| 目标用户场景 | 在电脑前干活，多 harness 协同 | 随时随地（飞书消息随时响应） |

**共享核心**（两个形态完全复用，不重复开发）：
- `MultiBackendAdapter` + 领域路由（多 harness 编排）
- durable 内核（TaskWorld / fold / effect / anchor / fencing）
- 会话管理与记忆（qwen-audio-agent 提供 + Fugue 扩展）
- 前台全双工 + 多端（WebUI / 飞书）

## 理由

- A 的独立价值是「多 agent 编排 + 会话记忆」，不是 C 的降级版；合盖休眠是物理边界，接受它、并在唤醒后无缝恢复，是诚实的产品定位。
- TaskWorld 接口已把「存储/队列/流」抽象出来（ADR-0009），换实现（本地文件 ↔ 云端）不改编排代码——这正是支撑双形态的地基。
- durable-harness 的完整形态（进程由平台管 + 状态持久化）在 C 形态下才真正等价；A 形态用 launchd 实现本地等价物。

## 后果

- **收益**：两个形态覆盖两类场景；核心只开发一次；TaskWorld 抽象的价值兑现。
- **代价**：C 形态需云端基础设施（部署、Postgres/Redis、进程监督），是后续工程；A 形态需 launchd 守护 + 唤醒恢复。
- **实现顺序**：先 A（守护 + 唤醒恢复，本地已跑通，零依赖），后 C（上云，复用 Hermes 云主机）。
- **风险**：C 形态的「会话记忆跨设备」需重新审视（本地记忆 vs 云端记忆的同步/隐私）。
