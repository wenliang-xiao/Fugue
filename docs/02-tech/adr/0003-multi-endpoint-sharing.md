# ADR-0003 多端共享：分时互补（takeover），而非同时并发

- 状态：已采纳
- 日期：2026-10-10

## 背景

产品要求两个入口（语音 App + 飞书文本）共享同一个 Agent 的会话、任务与记忆（REQ-003）。qwen-audio-agent 的 Gateway Client Protocol 有一条硬约束：**一个 owner 同一时刻只能有一个 active Client**（`client_occupied`），另一 client 需经 `session.takeover` 顶替，或用 `session.replay` 恢复错过的任务事件。

## 决策

**采用"分时互补"模型：两个 client 轮流连接同一个 Gateway，靠 takeover 切换 + replay 恢复。不实现"同时在线"的多 client 并发。**

## 理由

- 真实使用场景是分时的：用户要么在语音通话，要么在刷飞书，极少"一边打电话一边打字"。两个入口互补而非并发。
- 任务队列、会话记忆、权限状态都在 Gateway 层持久化，client 只是 I/O 层——**分时切换 + replay 即可达到"状态一致"，无需改上游 core**。
- 语音通话期间任务完成，由语音通道直接播报（上游原生能力），飞书无需同时推送，不存在"必须并发"的场景。

## 后果

- **收益**：零改动复用上游机制，架构大幅简化，MVP 可快速落地。
- **代价**：不支持"语音通话中飞书实时同步推送"；切换瞬间有 lease 交接（已由 takeover 机制处理）。
- **风险/未来**：若未来出现真实并发需求（如团队共用、一个 owner 多设备同时在线），需改上游"单 client 约束"（架构级），届时追加新 ADR 推翻本决策。
- **备选**：改上游 core 支持多 client 并发（成本高，非 MVP 必要）。
