## 打断（barge-in）根因定位与修复（2026-10-22）✅

**用户诉求**：只要一开口说话，前台（播报）立刻闭嘴。

**根因**（真实日志 `~/.config/qwaudio/state/logs/gateway.log` + 协议层监控定位）：
- 豆包 Seeduplex 用 `conversation.item.input_audio_transcription.started` 表示「用户开始说话」；
- 但 qwen 的打断监听的是 `input_audio_buffer.speech_started`（`realtime-input-runtime.mjs` 的 `#startSpeech`）；
- **doubao-seeduplex 协议层没有做这个事件映射**，导致 qwen 永远收不到打断信号，`speech_started` 日志 0 次。
- 佐证：监控 `[seeduplex-in]` 打印出 Seeduplex 返回了 `input_audio_transcription.started/delta/completed`（用户语音转写），但从未返回 `input_audio_buffer.speech_started`。

**修复**：`patches/qwen-audio-agent+2.0.1.patch`（patch-package，不 fork 上游仓库）——在 `doubao-seeduplex-protocol.mjs` 的 `normalizeIncoming` 里映射：
```js
if (event.type === 'conversation.item.input_audio_transcription.started') {
  return { ...event, type: 'input_audio_buffer.speech_started' }
}
```

**验证**：用户实测通过。日志出现 `realtime.provider.speech_started` + `realtime.playback.cancelled`（开口即打断）。

**踩坑复盘**（本次打断问题排查走过的弯路，供后续借鉴）：
1. 归因「播报太长导致音频积压」——方向部分对（背压断连确实是播报全文导致），但和「打断不了」无关。
2. 归因「麦克风没开」——日志 inputEnabled 确实多次 false，但不是根因。
3. 归因「turn_detection 漏传」——加 turn_detection 无效，已撤销。
4. **正确路径**：加临时日志打印 Seeduplex 返回的所有事件类型 → 发现「有转写、无 speech_started」→ 定位协议层缺事件映射。

**教训**：排查打断/实时链路问题时，先抓「服务端到底返回了什么事件」，而不是从代码推理「应该返回什么」。

## A 形态守护 · launchd 常驻 + 崩溃自愈（2026-10-22）✅

**用户洞察**：durable 只解决「崩溃恢复」，不解决「进程常驻」。Fugue 之前 `npm start` 前台进程，关终端即挂，只做了一半 durable。电脑合盖/休眠是本地跑的物理天花板，durable 也救不了（睡眠≠崩溃）。

**决策（ADR-0011）**：A（本地个人助手）与 C（云端常驻）两个产品形态，共享编排核心（MultiBackendAdapter + durable 内核 + 会话记忆），仅部署形态分化。A 的独立价值 = 全双工多 agent 编排 + 会话管理/记忆。

**A 形态守护实现**：
- `scripts/daemon.ts`：launchd 管理（install/uninstall/start/stop/status）。
- plist：`KeepAlive=true`（崩溃自愈）+ `RunAtLoad=true`（登录自启）+ 后台运行。
- 踩坑：`node_modules/.bin/tsx` symlink 在 launchd 下 `env node` 找不到（exit 127）；改用 `process.execPath` + `tsx/dist/cli.mjs` 绝对路径。
- **验证**：`daemon:install` 后 launchd state=running、3101 稳定监听、Gateway 常驻。
- 测试：100 测试全绿（+6 daemon plist 契约）。

**完整闭环**：进程崩了 launchd 秒级拉起 → `rebuildTaskMap()` 从 data/tasks/ 恢复任务 → 用户无感知。这才是本地等价于 durable-harness 的完整形态。
